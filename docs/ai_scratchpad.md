- The Vercel deploy runs `next build`, which type-checks every `.ts`/`.tsx` in the repo, including `scripts/` and tests. One type error anywhere fails the deploy even when `next dev` serves the page without complaint, so unverified work should get a clean `npx tsc --noEmit` before it is committed. The two "Dynamic filesystem access causes tracing of the whole project" notices from the learning-progress share image route are long-standing warnings, printed last in the log; they are not what fails a build.
 - In a Drizzle `sql` sub-select, never correlate with an interpolated column (`${table.column}`): when the outer query has no join the column prints without its table, and inside the sub-select that bare name resolves to the inner table, so the row is compared with itself. Alias the inner table and name the outer one in full (`from ${inner} as i where i.x_id = ${outer}.id`), as in `lib/db/queries/ministry-sql.ts`, and pin the printed SQL with `QueryBuilder().toSQL()` (`lib/community/ministry-sql.test.ts`). Interpolating an outer-table column inside an aliased sub-select is the same bug in another shape: `${s.users.id}` rendered as bare `"id"` and bound to the inner table, crashing `listFollowUpOwnerCandidates`/`resolveFollowUpRequest`/`changeFollowUpOwner` with `text = integer` (found live 14 October; admin follow-up resolution was broken). Correlate with raw outer text (`= users.id`) when the outer query FROMs that table unaliased, and verify admin/owner queries by executing them, not by reading.
- PPC DB routes need `DATABASE_URL`. The default Neon HTTP Drizzle client cannot run transactions; use the dedicated Neon `Pool` transaction client for atomic writes and `DATABASE_URL_UNPOOLED` with `Pool`/`Client` for bulk scripts. Queries sharing one transaction connection run sequentially; parallelise only across independent connections.
