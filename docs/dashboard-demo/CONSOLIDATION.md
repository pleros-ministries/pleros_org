# Dashboard consolidation: decisions and migration map

9 October 2026. Based on the current checkout, not historical handoff claims. This is a proposal; production functionality and permissions have not been changed.

## Recommended approach

Keep the new presentation shell and bring existing features into it, route by route. Keep canonical `/dashboard` URLs, authentication, server actions, enrolment guards and stored IDs. Preview remains a separate fixture adapter. Never make the synthetic `as` switcher available as a production identity mechanism.

Start with the shared shell and home. Then migrate Devotion and Welcome Pack, SOGP and its assessments, Community, My disciples and ministry reporting. Implement new reporting declarations and church hierarchy only after their specific policy decisions. Each stage needs populated, mobile, keyboard and permission checks against the existing feature before replacement.

## Migration sequence

1. **Shell and capability adapter:** extract pure presentation, keep server session identity, real sign-out, permitted links, deep links and focused onboarding layout. No fake role switch in live UI.
2. **Home / devotion / Welcome Pack:** compact existing home cards, real progress summaries; migrate Prayer Watch/Bible reading, Podcast and Welcome Pack with canonical actions/reminder controls.
3. **Training:** Pre-SOGP, SOGP calendar/course/audio/assessment/review, leaderboard/referrals/certificate and Discipleship Journey. Preserve dates, release gates and stored progress.
4. **Community and My disciples:** reuse feeds/groups/messages/Ask Pleros and their privacy rules; migrate led/joined groups, invitations/check-ins/prayers/consented WhatsApp and owner contacts into the new presentation.
5. **Reporting:** reuse compiled devotion, activities/history/contacts/export rules; add approved declarations and meeting-role fields through reviewed migrations. Do not run production migrations as part of visual consolidation.
6. **Church oversight:** only once the responsibility tree and visibility matrix are agreed; implement server-side scoped queries and status-only access independently of private notes/contacts.

## Decisions recorded and remaining questions

- **Resolved:** church unit leaders get submission status only for assigned people, including the three categories and explicit Nil versus missing. Private notes/contact details remain restricted. This is a product decision; production enforcement still needs an approved assignment relationship and server-side scope checks. No implicit access from community moderator title.
- **Resolved:** the Pastor sees report status, recorded activities and per-person numbers across all branches; Branch Pastors see the same within their own branch. Ministry notes/contact details are excluded from organisational oversight; unrelated private messages/prayers/answers remain protected. Existing separately authorized access is preserved.
- **Resolved:** meeting reporting roles: Leader = whole-meeting attendance + what was taught; Worker = attendance of the people with them; Member = own attendance. Name/location optional; teaching/prayer meeting kinds remain. This does not add auth roles.
- **Resolved:** reporting write window is today plus the previous seven Lagos days, inclusive; older dates are view-only. This replaces the old today-plus-two rule and is implemented in the branch, not production.
- **Resolved:** missing-report reminders use in-app notifications plus opted-in push; automatic reminders run at 8 pm Lagos time for that day’s incomplete report, with manual reminders also available, capped collectively at one reminder per person per Lagos day; reminders-only, no penalties or access restrictions, no live sends activated.
- **Resolved:** Devotional prefills automatically from canonical sources, then requires one daily confirmation. No re-entry or duplicate activity storage; missing source facts remain visibly not recorded.
- **Resolved:** church hierarchy is Pastor → Branch Pastor → Unit leader → Worker. Each leadership tier can also lead its own disciples; discipleship membership is separate from organisational supervision. The Pastor and Branch Pastors manage appointments/assignments; unit leaders do not. Branch Pastors manage only their own branch; the Pastor manages all branches. Production assignment storage/enforcement remains unresolved.
